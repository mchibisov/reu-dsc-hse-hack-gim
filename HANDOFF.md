## Самое важное сейчас

**Код и локальный Docker проверены, но обновление действующего облачного бота ещё не выполнено.** Push в GitHub не развёртывает Vercel автоматически. Полный живой сценарий текущей версии не подтверждён.

Пользователь предоставил токен сообщества и свой тестовый VK ID. Реальная read-only диагностика подтвердила:

- Токен действителен, есть права сообщений/управления/документов; сообщество `242476311` доступно.
- Рабочий Callback на `gim-volunteer-bot.vercel.app` имеет `status=ok`, `message_new=true`, API `5.199`. Есть также старый unconfigured Callback: его не удаляли и причиной сбоя не объявляли.
- Messages API доступен, в истории других диалогов есть реальные ответы бота. В одном ранее наблюдались вопросы 17/19–19/19: тогда использовались старый банк/версия. Текущий deployed SHA по этому не определён.
- Для указанного пользователем тестового аккаунта последняя проверка вернула **пустую историю**. Пользователю предложено открыть https://vk.me/club242476311, разрешить сообщения и отправить «Начать». Подтверждение отправки пока не получено.
- `/health` отвечает HTTP 200; он **не проверяет БД, очередь, AI и доставку VK**.

Токен находится только в локальном игнорируемом `.env`. В нём **пусты** `DATABASE_BOT_URL`, `DATABASE_WORKER_URL`, `DATABASE_STAFF_URL`, `RECRUITMENT_ID`, `LLM_API_KEY`. Поэтому локальный `check-db` останавливается с понятной диагностикой; полноценный локальный бот с реальными данными не запущен. Доступов/подключённых инструментов Vercel и Supabase нет. Не выдумывать UUID/DSN и не подменять рабочую БД тестовой.

## Что исправлено и принято

1. **Очередь и задержки обычных ответов.** В serverless-диспетчере выделены обработчики доставки и входящих сообщений; они не исчезают, пока долгий AI держит общую аренду. При малом остатке бюджета обычные события продолжают обрабатываться, новый анализ откладывается. TaskGroup отменяет соседние задачи до освобождения аренды. Регрессии проверены настоящей SQL-очередью, внешние VK/AI в этих тестах заменены управляемыми границами; production-ускорение не измерено.
2. **Анкета по новому поручению пользователя:** 18 основных вопросов. Исходный вопрос 8 «ВУЗ (Другое)» / `university_other` исключён; бывший 9 `faculty` называется **«Факультет, направление»** и после перенумерации отображается восьмым. Импорт понимает исходный DOCX19 и обновлённый DOCX18, выдаёт18 основных и11 библиотечных уточнений.
3. **Миграция без удаления старых ответов:** `database/supabase/migrations/20261022030000_questionnaire_revision.sql`. Retired-шаблон скрыт/необязателен, pending/active старый вопрос переводится в skipped, current pointer снимается; уже отвеченный сохраняется. Stale template нельзя создать повторно. Ранее применённые миграции не переписывать.
4. **Исправлена найденная повторной приёмкой регрессия:** новый ответ после миграции мог дописаться к предыдущему `university`. Ingress теперь учитывает последний действительно показанный skipped-вопрос и порядок `cmid`; следующий уже показанный вопрос имеет приоритет. Проверены поздние и переставленные события.
5. **Исправлен нагрузочный скрипт:** динамический прогресс вместо жёсткого «из19», отдельный локальный `TEST_DATABASE_URL`, selector loop для Windows.
6. **Очистка после snapshot:** удалены28 legacy/дублирующих файлов: старый public-runtime и его тесты, две старые public-миграции, дубли Docker/Compose/env/README; удалены неиспользуемые Settings/методы. Остался один актуальный Dockerfile, compose.yaml, .env.example и private PostgreSQL runtime. CI и Windows setup приведены к нему. История/данные/секреты не удалялись.
7. **Запуск и упаковка:** исправлены UTF-8/BOM, pytest discovery, упаковка ranking config и bootstrap; в CI создан тестовый env для Compose.

Пользователь запретил менять модель: сохраняется `deepseek/deepseek-v4.1-flash-1017` через Polza. Для новых анкет действует заданная пользователем формула **50% мотивация /35% опыт /15% обучение и нагрузка**, серверный расчёт0–3 и дробный рейтинг. Это не подтверждённая музеем и не независимо валидированная формула. Старые анкеты сохраняют закреплённую рубрику. Окончательное решение принимает человек.

## Архитектура и запуск

- Python3.12; private schema `gim` в PostgreSQL/Supabase; три разных ограниченных LOGIN: bot/worker/staff. Redis/ARQ не нужны.
- Облако: `api/index.py` → Callback → сохранённое SQL-событие → pg_net /work + recovery Cron →4 обработчика. В облаке закрытые XLSX хранятся в PostgreSQL.
- Docker/свой сервер — альтернативный Long Poll gateway+worker, локальное private storage. Не запускать конкурирующий gateway/worker того же сообщества параллельно действующему облаку.
- Нужны рабочие `.env`/DB/recruitment/API, а не только VK_TOKEN. Инструкции: [README](README.md), [новая установка](docs/setup-from-scratch.md), [облако](docs/deployment-guide.md).
- Проверки: `python -m gim.shared_main check-db`, затем `check-vk`. `python -m gim.shared_main run` либо `docker compose up --build -d` только после подготовки БД и выбора единственного транспорта.
- Тесты направлять исключительно в disposable PostgreSQL; `TEST_DATABASE_URL` не должен вести на production. Windows/psycopg использует selector event loop. Локальный venv: `.venv/Scripts/python.exe`.

## Конкретный следующий шаг

1. **Продолжить живой тест:** дождаться, когда пользователь напишет «Начать» в сообщество с согласованного тестового аккаунта. На исходном компьютере ID сохранён в ignored `runtime/vk-test-actor.json`; в новой среде без файла запросить ID у пользователя. Токен брать только из локального ignored.env/защищённого хранилища, не из этого handoff.
2. Создать новый каталог результатов S011-03, скопировать туда [read-only проверку диалога](results/2026-10-22-bootstrap-s011-live-vk-02/check_dialog.py), запустить её с тестовым ID. Скрипт сохраняет только обезличенные метаданные; не перезаписывать результаты02. Проверить новый входящий старт, фактический ответ/задержку и число вопросов. Не отправлять сообщения другим участникам и не объявлять историю старого диалога новым тестом.
3. Для **обновления до текущего кода18вопросов** получить доступ к существующим Vercel/Supabase, runtime DSN/recruitment и выбранной модели; секреты вводить локально/в защищённых env, не коммитить. Наличие VK_TOKEN этих доступов не заменяет.
4. Контролируемое обновление существующего production: приостановить новые /work и recovery Cron, дождаться старых workers → применить новую миграцию → redeploy → возобновить очередь. Callback продолжает сохранять входящие события; очередь/анкеты не очищаются. Причина порядка: старый worker может повторно создать удалённый вопрос до обновления.
5. После обновления пройти полную новую анкету:18 базовых, ожидания, до3 уточнений, сохранение/подача, уведомления, настоящий AI, карточка/рейтинг/ручная оценка, скачивание Excel. Отдельно проверить старую незавершённую анкету и поздний ответ. Затем измерить экспертное качество и удобство людьми.
