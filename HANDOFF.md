## Актуальные продуктовые решения

- Все взаимодействия через личные сообщения сообщества VK; веб-кабинет не нужен. Нет загрузки резюме, PDF и ручной правки оценки/направления/заметок.
- Сохранять исходные смысловые поля анкеты; весь опрос с уточнениями — целевые5–7мин, пока не измерены на людях. Уточнения после основной анкеты, про конкретный прошлый опыт и личные hard/soft skills; не ситуационные задания. Не повторяться.
- Пять направлений: мероприятия; квесты/мастер-классы; фонды; инклюзия; медиа. Не изучать страницу VK кандидата.
- Оценка0–3 по пяти заранее заданным группам, объяснения и точные цитаты, summary/направление/вопросы для интервью — только сотруднику. Критерии модель не придумывает. Текущая числовая рубрика предварительная: качество относительно музейных экспертов и утверждение весов не доказаны. Решение о приёме принимает человек.
- При отказе модели анкета сохраняется, используются библиотечные уточнения, оценка отсутствует; не подставлять фиктивный0. Вход модели исключает контакты, VK ID и последующие исходы участия; доступное время кандидата не равно историческим часам волонтёрства.
- **Последнее уточнение доступа:** любой, кто знает секретный код, получает Excel. Согласованный flow — `/excel КОД`, одноразовая выдача в личный диалог, без остальных прав куратора. В анкете/помощи/кнопках не показывать вопрос «введите секретный код». Удаление отправленного пользователем сообщения не требуется.
- Redis/ARQ удалены. Нужны логирование, SQL-очередь, ограниченные повторы/восстановление после аварии, тесты, Docker. Ориентиры первоначального запуска:12ч, небольшой бюджет около2000руб.,90одновременных кандидатов; полная нагрузочная/производственная приёмка не выполнена. Программа музея — до100 участников, не искусственное ограничение числа заявок.
- Секреты и `.env` **не публиковать**. Ключи уже сохранены локально; не просить прислать их повторно и не вставлять в HANDOFF/отчёты/коммиты.

## Модель: установленная причина незавершённости

**Текущий выбор пользователя:** `LLM_BASE_URL=https://polza.ai/api/v1`, `LLM_MODEL=deepseek/deepseek-v4.1-flash-1017`. Ключ находится в `gim_bot/.env` под `POLZA_API_KEY`; активный `LLM_API_KEY` ещё пуст. Endpoint/model подтверждены API, не являются предположением.

Проверка Polza: `/models`200, точная модель есть, короткий strict JSON200. Но полный `Provider.analyze` получил HTTP200 с **finish_reason=length, content_length=0, completion_tokens=1800, reasoning_tokens=1800**. В `src/gim_bot/analysis.py::Provider._generate` жёстко стоит `max_tokens=1800`; весь бюджет ушёл в рассуждения. Безопасный fallback вернул None. `Provider.followups` прервался по локальному лимиту3с. **Это не ошибка ключа и не отсутствие модели.**

Следующий технический шаг: проверить официальный Polza API на документированный контроль reasoning для этой модели, затем тестируемо адаптировать запрос/бюджет/таймауты и повторить полный synthetic pipeline. Не заменять выбранную модель молча и не объявлять готовность по одному короткому JSON ответу.

Groq ранее успешно прошёл models/chat и настоящий Provider.analyze (5критериев) / followups (3вопроса) на synthetic, модель openai/gpt-oss-120b. Ключ — локально `GROQ_API_KEY`. Пользователь затем выбрал Polza: Groq не включён и не назначен автоматическим резервом.

Все внешние проверки использовали только synthetic ответы из scripts/check_groq.py; реальные2анкеты из SQLite провайдерам не отправлялись и не ставились на повторный анализ.
