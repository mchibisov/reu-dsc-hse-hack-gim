# Компонент БД ГИМ

Основание: запрос Макса 21.10.2026, оригинальные DOCX, QA жюри, описание кейса, PDF направлений, XLSX 2024/2025, reviewed-проект 12 таблиц. Репозиторий на момент проверки пуст, публичный. Закрытые материалы и персональные данные не включаются в Git.

## Назначение и границы
Постоянная анкета и история персонального диалога, оценки 0–3 с проверяемыми источниками, серверный доступ сотрудников, приватные файлы, согласованные данные Excel. Бот, LLM и генерация файлов остаются другим участникам. Решение о приёме принимает человек. 100 — вместимость программы, не лимит заявок. Целевая проверка — 50 параллельных кандидатов.

## Выбранный вариант
12 прикладных таблиц в закрытой схеме gim. Python psycopg 3 и ограниченный пул. Роли PostgreSQL: bot, worker, staff; у staff нет прямого доступа к таблицам, только ограниченные функции, сверяющие подтверждённый сервером VK ID и актуальное членство. Публичные роли Supabase не имеют доступа. Первый администратор создаётся оператором, остальные — действующим администратором сообщества. VK callback/signature проверяет Python-сервис до вызова контракта; поля payload не являются удостоверением личности.

Redis/ARQ — единственный исполнитель. Outbox PostgreSQL хранит намерения, стабильные ключи, результаты и время повторной публикации. Исполнитель не выбирает задания из PostgreSQL самостоятельно. Потеря Redis восстанавливается публикацией незавершённых намерений. Доставка внешнему VK как минимум один раз; стабильный random_id уменьшает дубли, абсолютная exactly-once не обещается.

Вариант только с PostgreSQL-очередью проще по инфраструктуре, но меняет выбранный командой механизм исполнения. Вариант FSM в Redis создаёт два источника состояния и отвергнут.

## Инварианты
- Вопрос и намерение отправки фиксируются одной транзакцией до отправки; повторный request_key возвращает сохранённую формулировку. CAS по версии и блокировка заявки исключают потерю параллельных ответов.
- Ответы неизменяемые, имеют последовательную ревизию и дедупликацию входного события в рамках сообщества. При конкурентных сообщениях к устаревшему вопросу ответ не переадресуется на следующий автоматически.
- Полная дата рождения и её происхождение хранятся явно; частичная историческая дата остаётся текстом, не выдумывается. Согласие и все обязательные вопросы проверяются до подачи.
- Банк и рубрика замораживаются при открытии. Реальные критерии поставляет команда: пять групп из оригинала не означают утверждённую формулу. Тестовая рубрика не используется как музейная.
- Ревизия включает изменения ответов и готовых резюме. Оценка хранит точный список последних ответов на момент ревизии и ID/хэши резюме. Цитата допускается только из этого списка, проверяется подстрока и тот же кандидат. История неизменяема. Ручная оценка приоритетна для одного снимка; устаревшая оценка помечается.
- Все файлы версионируются, готовый объект неизменяем. XLSX набора не связан с кандидатом. Доступ через серверные проверки и короткую signed URL; bucket приватный.
- Экспорт читает все четыре набора данных в одной REPEATABLE READ транзакции; NULL отличается от 0; полные ответы не обрезаются. XLSX-исполнитель обязан записывать текст как строки (защита от formula injection).
- Аудит содержит только идентификаторы, действие и безопасные метаданные. Логи не включают полный payload, ответы, секреты.

## Проверка
Интеграционные тесты реального PostgreSQL: миграции, права, заморозка, 18+/согласие/обязательные вопросы, вопрос до ответа, дубли и конкуренция, цитаты и снимки резюме, ручная оценка, повторная публикация outbox, экспорт и 50 кандидатов. Отдельная облачная smoke-проверка не заменяется локальным тестом. Проверка качества оценок требует реального LLM/baseline и экспертных меток, не является свойством схемы.
