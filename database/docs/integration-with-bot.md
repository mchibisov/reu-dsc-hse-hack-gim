# Интеграция с ботом ветки Vova

**Историческая запись до S003.** Интеграция уже реализована в `gim/shared_*.py`; актуальны [README-SHARED](../../README-SHARED.md) и [S003](../../docs/specs/S003-shared-db-integration.md). Упоминания ARQ ниже не относятся к текущему runtime: он использует PostgreSQL SQLQueue без Redis, а XLSX хранится приватно локально.

Перед публикацией компонента обнаружена новая ветка `Vova`, commit `ff0b44bdd38ec25868615af2ad2505f9fe30dece` (она отсутствовала при первом клонировании). Ветка Макса продолжает эту историю, а компонент добавлен в `database/`. Файлы бота, его README, старые миграции и Compose не изменены.

## Важное несовпадение контрактов

Имеющийся `gim/db.py` использует таблицы без схемы, поле роли непосредственно в users и PostgreSQL-очередь `jobs` с claim/lease/renew. Новый компонент использует **private gim schema**, отдельные staff_members, сохранённые dialog_questions и **ARQ** как единственный исполнитель. Эти модели не совместимы простой заменой DATABASE_URL. Нельзя запускать обе очереди для одной рабочей анкеты.

Запуск нового MVP компонента выполняется **из database/** по его docs/connection.md; корневой compose.yaml запускает существующий самостоятельный вариант бота и не является запуском нового компонента. В Supabase старые корневые миграции не применялись, jobs отсутствует.

## Что должен сделать участник бота

1. При переходе использовать `gim_db.Repository` с отдельным bot DSN. Убрать вызов старого `Database.migrate/bootstrap`, выдающий admin через users; bootstrap теперь только операторский.
2. После проверки VK identity/group создать/найти application. Сохранять подготовленный вопрос через prepare_question до VK-вызова, входной ответ — через record_answer с явным question_id и revision.
3. Состояние планировщика брать из dialog_context, не из самостоятельной FSM Redis. Хранить полный raw answer + parsed value; для даты/направлений/контактов вызвать соответствующие методы.
4. Вместо enqueue/claim/finish/renew legacy jobs подключить topic handlers ARQ и издатель outbox. На cutover остановить старые `gim.main worker` и `report-worker`; незавершённые legacy jobs сначала обработать старым контуром или явно перенести с дедупликацией. Старую и новую очереди одновременно не подключать к live VK.
5. scoring adapter возвращает критерии, цитаты, summary и рекомендации по snapshot нового контракта; подменять результат старым score+summary без evidence нельзя. Согласовать rubric_version с Гермесом.
6. Экспортёр получает четыре набора из сохранённого snapshot, пишет приватный файл и подтверждает FileRepository.finish. Вместо локальной папки reports использовать приватный Storage и staff access check.
7. Кабинет/команды сотрудника получают verified VK из серверной сессии, затем используют staff DSN + export_bundle/curator_evaluation/decide/set_staff. Не передавать actor из непроверенной кнопки.

Это работа интеграции, а не автоматическое переписывание чужого бота. Изолированный компонент БД уже проходит свои реальные DB/Redis тесты; сквозной запуск существующего бота с новой моделью требует этих изменений и отдельного теста команды.
