# Волонтёры ГИМ — VK-бот

Основная версия — **`main`**. Хранилище — **PostgreSQL в Supabase**, закрытая схема `gim`. **Redis и ARQ не используются**: события и фоновые задачи хранятся в PostgreSQL.

Кандидат проходит музейную анкету, получает уточнения по своим ответам и подаёт заявку. Сотрудник получает уведомление, список заявок, оценку 0–3 с цитатами, резюме, вопросы для собеседования и Excel. Окончательное решение принимает человек.

## Архитектура

```text
VK → gateway → PostgreSQL: входящие события → worker
                                              ├─ вопросы и ответы
                                              ├─ LLM: уточнения и анализ
                                              ├─ уведомления сотрудникам
                                              └─ XLSX из сохранённого снимка
```

Gateway и worker запускаются раздельно; у worker по умолчанию четыре асинхронных обработчика. Повторы событий отсекаются, задачи используют аренды с heartbeat и защитой от устаревшего обработчика. Исходящие сообщения одного кандидата сохраняют порядок при повторных попытках. Несколько worker могут работать с общей БД; для файлов на одном сервере используется общий закрытый volume.

В БД 13 таблиц: пользователи, сотрудники, наборы, шаблоны вопросов, заявки, заданные вопросы, ответы, оценки, файлы, входящие события, исходящие задачи, журнал действий и позиция Long Poll. Доступ бота, воркера и сотрудника разделён тремя ролями. Подробности: [контракт БД](database/docs/contracts.md), [настройка подключений](database/docs/connection.md).

## Подготовка БД

Оператор применяет все пять миграций из `database/supabase/migrations` к целевой Supabase БД через `python -m gim_db.migrate` **из каталога `database/`** с `DATABASE_ADMIN_URL`. Пароль оператора не передаётся runtime. Уже применённые миграции не редактируются.

Нужны три отдельных LOGIN, созданных `database/scripts/provision_runtime.py`, с ролями `gim_bot`, `gim_worker`, `gim_staff`. Затем оператор загружает музейный банк вопросов и реальные описания направлений, утверждённую командой рубрику, регистрирует сотрудников и активирует набор. Скрипты и команды описаны в [инструкции оператора](database/docs/connection.md).

Нельзя запускать `python -m gim.main migrate` или применять корневые `migrations/` к этой БД: это отдельная старая public-схема.

## Запуск

1. Python 3.12: создать `.venv` и установить `pip install -r requirements.shared.txt`. На Windows можно открыть `setup_shared.cmd`.
2. Скопировать `.env.example` в `.env`. Заполнить `VK_TOKEN`, `VK_GROUP_ID`, `RECRUITMENT_ID`, `DATABASE_BOT_URL`, `DATABASE_WORKER_URL`, `DATABASE_STAFF_URL`. Для Supabase использовать SSL и отдельные runtime-подключения; параметры pooler — в инструкции оператора.
3. Для модели заполнить `LLM_API_KEY`, проверить `LLM_BASE_URL` и `LLM_MODEL`. Текущий провайдер — Polza, выбранная модель — DeepSeek. Ключи хранятся только локально, в Git не добавляются.
4. Остановить прежний Long Poll процесс того же сообщества. Выполнить `python -m gim.shared_main check-db`, затем `check-vk` и `run`; на Windows — `run_shared.cmd`.

Для сервера:

```sh
docker compose up --build -d
```

Обычный `docker compose` и корневой Dockerfile запускают **общую Supabase-версию**. `compose.shared.yaml` и `Dockerfile.shared` оставлены как совместимые имена. PostgreSQL берётся из внешних DSN, дополнительная локальная БД и Redis не поднимаются. Создание сообщества, сообщения и Bots Long Poll с `message_new` должны быть настроены в VK. Сотрудник должен разрешить сообщения сообщества.

## Работа сотрудника

- `/admin` — команды, доступные активному сотруднику своего сообщества.
- `/top`, `/stats` — рейтинг и сводка.
- `/application UUID` или `/candidate UUID` — карточка, резюме и основания оценки.
- `/export` — общая XLSX; `/export UUID` — отдельная анкета. Четыре листа: «Анкеты», «Ответы», «Собеседование», «Сводка». Исходные ответы сохраняются полностью, длинные поля продолжаются в следующих строках.

Доступ подтверждается по VK ID и активной записи `staff_members`; знание команды не даёт прав. Дополнительно `/export СЕКРЕТНЫЙ_КОД` выдаёт Excel человеку без staff-роли: кандидаты, ответы, summary и сводка текущего набора. Код задаётся локально через `EXCEL_ACCESS_CODE`, пустое значение отключает этот способ. Разрешение действует только для одной выгрузки и не открывает `/top`, `/stats` или карточки. После пяти ошибок за 10 минут выдача блокируется до истечения окна. Команда не предлагается в анкете и помощи. Код удаляется из сохраняемого VK-события до записи в БД; перед выдачей файла право проверяется повторно. При смене кода перезапустите gateway и все worker.

## Модель и рубрика

Вопросы основной анкеты берутся из БД. После неё модель получает содержательные ответы и историю уточнений; каждый новый вопрос сохраняется до отправки. Уточнения должны опираться на точную цитату и не повторять заданный текст, общий лимит — до трёх. Без ключа или при сбое генерации используются подходящие библиотечные уточнения; автоматический балл не ставится.

Критерии и веса предоставляет команда, модель не придумывает их. Текущий адаптер поддерживает **сумму критериев с общим максимумом 3**, округление до целого с 0.5 вверх. Это технический вариант MVP, который команда должна явно утвердить в `rubric.scoring_rule`; `approved_by` обязателен. Для явного согласования в рубрике указывается `scoring_method: "sum_round_half_up"`; без него анализ остаётся на проверку. Если нужна другая формула, её необходимо реализовать и проверить отдельно. При нехватке доказательств оценка не публикуется и нужна проверка сотрудником.

Каждая цитата сверяется с исходным ответом и его UUID; нельзя сослаться на другого кандидата. ФИО, email, ссылка VK и дата рождения не передаются отдельными полями модели; известные контактные строки и распознаваемые контакты маскируются в свободном тексте. Это фильтрация данных, не гарантия полного обезличивания произвольного текста. Исторические исходы — наработанные часы, приём, явка и удержание — не являются входом оценки.

Ошибка модели или отсутствующий ключ оставляют анализ для повторной попытки, а не создают нулевой балл. После пяти неудач задача отмечается failed; восстановление описано в [передаче MVP](HANDOFF.md). Анализ идёт в фоне после подачи, кандидат его не ждёт.

## Проверки и границы MVP

[Состав объединения и проверка](docs/integration.md). Автотесты используют синтетические данные и отдельную локальную PostgreSQL; API VK и LLM подменяются. Секреты, реальные анкеты и рабочая Supabase БД не нужны для CI. Проверка 50 одновременных записей в БД не означает измеренную нагрузку 50 пользователей с реальными внешними API.

Сайт, PDF, загрузка резюме, ручная оценка через бота и полное автоматическое удаление данных пока не входят в общий runtime. Удаление требует обращения к оператору. Файлы XLSX в MVP хранятся в закрытом volume, а не в Supabase Storage; резервировать нужно и БД, и volume. Запуск в реальном сообществе с выбранной моделью требует отдельной проверки после внесения локальных секретов.

## Старые варианты

`gim.main`, `compose.legacy.yaml`, `Dockerfile.legacy` и `compose.external.yaml` относятся к прежней public-схеме и сохранены для совместимости. Они не являются основным решением. Независимый прототип со своей SQLite-схемой не запускается параллельно с общей версией. Ветки и их исходные коммиты сохраняются в истории.
