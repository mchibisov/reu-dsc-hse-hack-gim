# VK-бот волонтёрской программы ГИМ

**Запуск с загруженной общей БД:** [README-SHARED.md](README-SHARED.md), `setup_shared.cmd` → заполнить `.env` → `run_shared.cmd`.
Он использует private schema `gim`, SQL-очередь и три runtime login, без Redis, LLM и оценок. [Спецификация](docs/specs/S003-shared-db-integration.md).

Ниже сохранена документация прежнего запуска с public-схемой из восьми таблиц; его миграции и команды не подходят для private БД.

MVP по схеме из восьми таблиц: `users`, `applications`, `answers`, `evaluations`,
`audit_log`, `inbox_events`, `jobs`, `files`. PostgreSQL хранит FSM, анкеты и очередь.
Redis и ARQ не используются. Один gateway принимает события; несколько worker
обрабатывают заявки, оценки и уведомления. Отдельный report-worker формирует Excel.

## Подключение к сообществу VK

1. Создайте сообщество VK или используйте тестовое, где у вас есть права управления.
2. В управлении сообществом включите сообщения. В разделе API создайте ключ
   сообщества с доступом к сообщениям и документам и правами, необходимыми для
   `groups.getLongPollServer`. Не используйте личный токен пользователя.
3. Включите Bots Long Poll API и событие `message_new` (входящее сообщение).
4. Скопируйте `.env.example` в `.env`. Укажите `VK_TOKEN`, положительный числовой
   `VK_GROUP_ID`, `ADMIN_VK_IDS` (VK ID сотрудников через запятую), пароль PostgreSQL
   и `CAMPAIGN`. `CONSENT_TEXT` необязателен: пустое значение начинает анкету сразу.
   В текущем локальном `.env` сообщество и администратор уже настроены.
5. Запустите:

```sh
docker compose up --build -d --scale worker=2
docker compose logs -f gateway worker report-worker
```

Точный интерфейс VK может отличаться. Проверяйте права и методы по официальной
документации: https://dev.vk.com/ru/method/groups.getLongPollServer,
https://dev.vk.com/ru/method/messages.send, https://dev.vk.com/ru/method/docs.save.
Нужен только исходящий HTTPS; публичный Callback URL для Long Poll не требуется.
Один gateway на сообщество; масштабируются worker. Два контейнера по четыре
асинхронных worker по умолчанию дают восемь обработчиков.

Миграция предназначена для **новой БД**. Для уже существующей БД команды сначала
сравните точный DDL: схема-картинка не задаёт все SQL-типы, ограничения и индексы.
Supabase поддерживается через `DATABASE_URL` с прямым или session-pooler
PostgreSQL-подключением. Задайте URL и используйте альтернативную конфигурацию:

```sh
docker compose -f compose.external.yaml up --build -d --scale worker=2
```

Transaction-pooler не подходит для session advisory lock gateway.

## Проверка вручную

Напишите сообществу `Старт` или `/start`. Если настроен `CONSENT_TEXT`,
бот сначала покажет его и попросит ответить `Согласен`.
Ответьте на основные вопросы, выберите направления номерами. Затем модель читает
всю сохранённую историю и выбирает один следующий вопрос либо завершает уточнения.
После каждого ответа история снова передаётся модели. Максимум — MAX_FOLLOWUPS
(по умолчанию три вопроса суммарно). Далее бот объясняет задачи и спрашивает про
ожидания и альтернативы; после этого формируется итоговая оценка.
Повторное `Старт` продолжает незавершённую анкету. `/status` показывает её статус.
Одна заявка на человека, сообщество и набор; новый набор задаётся `CAMPAIGN`.

Вопросы MVP адаптированы из предоставленных анкет и описания направлений.
Уточнения выбирает и формулирует только модель: поиск ключевых слов и шаблонная
подстановка удалены. Используется FOLLOWUP_URL либо прямой API модели.
При ошибке API состояние остаётся planning, ответы сохраняются, задача повторяется;
после исчерпания повторов куратор видит failed в /jobs и может вызвать /retry.
Каждый ответ сначала фиксируется в БД, а HTTP-запрос выполняется отдельной задачей
после коммита. Дополнения во время генерации тоже сохраняются, устаревший результат
не применяется. Сохраняется снимок заданных вопросов, чтобы обновление бота не
меняло историю анкеты. Прикреплённые документы сохраняются как ссылки VK в `files`
и отображаются куратору; содержимое резюме автоматически не разбирается.
PDF и отдельный сайт остаются опциональными компонентами вне этой части проекта.

Для сотрудника в том же диалоге доступны:

- `/help` — команды.
- `/top` — первые десять поданных анкет по баллу, с резюме.
- `/stats` — количество черновиков, поданных и оценённых анкет текущего набора.
- `/export` — XLSX со всеми анкетами текущего набора, ответами, оценками,
  критериями/цитатами и вопросами для собеседования.
- `/score UUID 2.5 Обоснование` — отдельная оценка человека с записью в audit_log.
- `/notify` — включение и выключение уведомлений «+1 заполненная заявка».
- `/application UUID` — полная заявка, вопросы собеседования и прикреплённые документы.
- `/jobs` — состояние фоновых задач текущего сообщества.
- `/retry UUID` — повтор неудачной оценки, подготовки уточнений или экспорта.
- `/whoami` — собственный VK ID и роль (доступно также кандидату).

Администраторы из `ADMIN_VK_IDS` создаются или повышаются до admin миграцией.
При удалении администратора уберите ID из конфигурации и измените роль в БД.
Куратора можно назначить доверенным SQL: `UPDATE users SET role='curator' WHERE vk_id=123;`.
Деактивация: `UPDATE users SET active=false WHERE vk_id=123;`.

## Контракт scoring-service

`SCORING_URL` — необязательный полный URL HTTP POST endpoint команды. Если он
не задан, итог формирует прямой API модели. Опционально передаётся bearer
`SCORING_TOKEN`. На вход идут только ответы заявки и выбранные направления.
Имя, источник набора и результаты последующего участия не отправляются.

```json
{
  "application_id": "uuid",
  "answer_revision": 12,
  "selected_directions": ["funds"],
  "rubric": {"version": "hermes-v1", "criteria": [{"code":"experience","description":"Описание утверждённого командой критерия","max_score":3}]},
  "answers": [{"id": "uuid", "question_code": "experience", "question_text": "...", "answer_text": "..."}]
}
```

Ожидается ответ:

```json
{
  "score": 2,
  "rubric_version": "hermes-v1",
  "rubric_snapshot": {"version":"hermes-v1","criteria": [{"code": "experience", "description": "Описание критерия команды", "max_score":3}]},
  "criteria_results": [{"criterion": "experience", "points": 2, "reason": "Обоснование", "answer_id": "uuid", "quote": "точная цитата ответа"}],
  "summary": "Краткое резюме",
  "interview_questions": ["Что уточнить на собеседовании?"],
  "recommended_directions": ["funds"]
}
```

Коды направлений: `events`, `projects`, `funds`, `inclusion`, `media`.
Рубрика в примере показывает только формат транспорта, не действующие критерии музея.
Критерии и их веса определяет команда; бот не создаёт их и не выдаёт запасной балл.
В RUBRIC_PATH задаётся файл с утверждёнными критериями. Рубрика фиксируется в
payload задачи перед обращением к API и не меняется при повторе. Проверяются
полный состав критериев, ограничения points, сумма баллов и цитаты. Положительный
балл без точной цитаты и answer_id не принимается. Переданную моделью версию рубрики
бот заменяет зафиксированной версией команды. Одинаковые проверки применяются
к прямому API и SCORING_URL. Без утверждённой рубрики автоматический балл не ставится.
Итоговое решение о приёме остаётся за человеком. Ручная оценка имеет приоритет
над модельной при сортировке, обе сохраняются.

При ненастроенном/недоступном скоринге анкета сохраняется и остаётся submitted.
После исчерпания повторов задача failed. После настройки сервиса можно повторить:

В боте: `/jobs`, затем `/retry UUID_задачи`. Или через доверенное SQL-подключение:

```sql
UPDATE jobs SET status='pending', attempts=0, available_at=now(), lease_until=NULL,
  lease_token=NULL WHERE kind='score' AND status='failed';
```

## Хранение и надёжность

Экспорты хранятся в общем Docker volume `reports`; в `files` — метаданные.
Это локальный Storage-адаптер, не Supabase Storage/S3. На одном сервере worker
видят один volume. Для разных серверов нужен общий Storage.

Входящие события и очередь записываются одной транзакцией, ответы и сообщения
бота — другой. Дубли VK отсекаются составным ключом. Задачи одного кандидата
упорядочены; другие анкеты обрабатываются параллельно. `SKIP LOCKED`, аренды,
heartbeat и lease_token защищают от конфликтующих worker. Исходящие сообщения
повторяются с тем же random_id. Промежуток между внешним VK-вызовом и записью
успеха не допускает абсолютной гарантии exactly-once.

JSON-подобные структурные поля PostgreSQL сохраняются как jsonb. Логи содержат
тип ошибки, ID задачи и её тип; ответы и токены не логируются. Ротация логов
настроена в Compose. Следите за `SELECT kind,status,count(*) FROM jobs GROUP BY 1,2;`.
Резервируйте оба volume: pg_dump PostgreSQL и файлы reports. Сроки хранения и
удаление персональных данных согласовываются с музеем до реального набора.

Long Poll checkpoint сохраняется в `audit_log` атомарно со входящими событиями.
Gateway использует session advisory lock: два процесса для одного сообщества
одновременно не запускаются. Сбой воркера не теряет сохранённые jobs.
Срок хранения истории на стороне VK ограничен; после длительного простоя сам VK
может потребовать сбросить позицию. Это отмечается в логах.

## Диагностика и локальный запуск

Локальные команды автоматически читают `.env`; переменные окружения имеют приоритет.
Ключ не входит в Git или Docker image. Для проверки конфигурации:

```sh
.venv/bin/python -m gim.main check-vk
.venv/bin/python -m gim.main check-db
```

При доступной БД можно запустить без Docker (в отдельных терминалах):

```sh
.venv/bin/python -m gim.main migrate
.venv/bin/python -m gim.main gateway
.venv/bin/python -m gim.main worker
```

`JOB_KINDS` ограничивает типы задач отдельного процесса; пустое значение разрешает
все типы. В Compose обычные и отчётные воркеры уже разделены. `WORKER_CONCURRENCY`
задаёт 1–8 асинхронных обработчиков на контейнер. Для закрытого тестирования
можно включить `TEST_MODE=true`: анкетирование станет доступно только ADMIN_VK_IDS.

## Исторические анкеты

Импортёр читает все листы, пропускает пустые оформленные строки, сопоставляет
столбцы по заголовкам и сохраняет экспертный балл. Повторный импорт того же файла
идемпотентен. Исторические анкеты не получают выдуманных VK ID и не создают
сообщений/задач скоринга. Часы, приём, явка и длительность участия хранятся отдельно
в `profile.historical_outcomes`, в ответы и вход скоринга не попадают.

```sh
.venv/bin/python -m gim.history '/path/Анкеты 2024 осень.xlsx' --campaign autumn-2024 --dry-run
.venv/bin/python -m gim.history '/path/Анкеты 2024 осень.xlsx' --campaign autumn-2024
.venv/bin/python -m gim.history '/path/Анкеты 2025 весна.xlsx' --campaign spring-2025
```

Предоставленные файлы проверены импортёром: 57 записей за 2024 и 55 за 2025.
Разные наборы хранятся раздельно; команды куратора показывают текущий CAMPAIGN.

## Контракт уточняющих вопросов

`FOLLOWUP_URL` получает POST с `application_id`, `answer_revision`,
`selected_directions`, `answers` (вся содержательная история), `direction_tasks`
и `remaining_questions`. Опциональная авторизация — bearer `SERVICE_TOKEN`.
Ответ — один из вариантов:

```json
{"action":"ask","direction":"funds","question":"Как вы проверяли номера предметов?"}
```

```json
{"action":"finish"}
```

Вопрос — до 1000 символов. Точные дубли и посторонние направления отвергаются;
семантические повторы должна исключать модель, получающая полную историю.
Допускается несколько разных уточнений одного направления в пределах общего лимита.
Старый формат с массивом `questions` заменён этим протоколом.

## Прямое подключение модели

В `.env` задайте `LLM_BASE_URL`, `LLM_API_KEY` и `LLM_MODEL`.
Для Mistral база — `https://api.mistral.ai/v1`; для OpenRouter —
`https://openrouter.ai/api/v1`. Имя модели должно соответствовать вашему провайдеру.
Клиент `gim/llm.py` использует chat/completions и JSON mode по
[официальной документации Mistral](https://docs.mistral.ai/api).
При заданном FOLLOWUP_URL он имеет приоритет для вопросов; SCORING_URL — для итогов.
Ключ VK не является ключом модели. Без ключа модели/внешнего сервиса дополнительные
вопросы не генерируются; шаблонного fallback больше нет.

`RUBRIC_PATH` указывает на JSON с полями `version` и непустым массивом `criteria`.
Каждый критерий задаёт `code`, `description` и `max_score`; сумма max_score должна
быть ровно 3. Критерии предоставляет команда, готового выдуманного набора в проекте
нет. Модель оценивает соответствие ответов этим критериям, формирует резюме,
рекомендации и вопросы для собеседования один раз после полного диалога.
Если это внешний файл в Docker, смонтируйте его read-only и укажите путь внутри контейнера.

## Локальные тесты

```sh
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/python -m unittest discover -s tests -v
```

Для интеграционных тестов укажите отдельную **тестовую** PostgreSQL БД:

```sh
export TEST_DATABASE_URL=postgresql://gim:password@localhost:5432/gim_test
DATABASE_URL="$TEST_DATABASE_URL" .venv/bin/python -m gim.main migrate
.venv/bin/python -m unittest discover -s tests -v
```

Без TEST_DATABASE_URL интеграционные тесты явно пропускаются. Реальные данные
из Excel в репозиторий не включены и автоматически не импортируются.

`REAL_POSTGRES_TESTS=1` включает тест параллельного захвата задач несколькими
подключениями. В GitHub Actions он выполняется на PostgreSQL 17. Новая ИИ-версия
также проверена на отдельном локальном PostgreSQL с включённым тестом конкуренции.
Рабочая база не используется тестами. Полноценная нагрузка 50 пользователей
с настоящим API модели отдельно не измерялась.
Интеграционные тесты очищают таблицы: запускайте их только на отдельной тестовой БД.
