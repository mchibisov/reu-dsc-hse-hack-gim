# Волонтёры ГИМ: VK-бот

## Быстрый локальный запуск

Двойной клик по `run_bot.cmd` запускает опрос в консоли без VK, Mistral, Docker и Redis. В терминале с установленными зависимостями: `python main.py`. Ответы сохраняются в `demo.db`, выход — `/quit`, новый опрос — `/delete` → `УДАЛИТЬ` → `/start`. Саммари и балл не формируются. Это проверка диалога; подключение к настоящему VK описано ниже. На текущем компьютере рабочий интерпретатор: `.venv\Scripts\python.exe`. Корневая `.venv` родительского проекта повреждена, её не выбирайте.

**Текущий режим по решению пользователя — без LLM.** Основной опрос, библиотечные уточнения по направлению, сохранение, Excel, сводка и уведомления работают без модели. Балл, модельное резюме и рекомендация отсутствуют. Ключ и модель локально очищены; интеграция Mistral отложена.

Полный целевой сценарий: исходные вопросы → уточнения по опыту → подтверждение кандидату; куратору — рейтинг 0–3, цитаты, краткое резюме, направление, интервью-вопросы, Excel и сводка. Решение о приёме принимает сотрудник. Нет сайта, просмотра страницы ВК, PDF, загружаемых резюме и редактирования оценки.

Полные требования: [спецификация](docs/specs/S002-gim-vk-bot.md), [план](docs/plans/S002-gim-vk-bot.md), [промпт](docs/prompts/S002-gim-vk-bot.md), [ход работы](docs/progress.md). Текст требований согласован в опросе, численная рубрика `gim-5-v1` предварительная и требует проверки на экспертной разметке.

## Тестовый запуск во ВКонтакте с этого ПК

Двойной клик по `run_vk.cmd` (или `python main.py --vk`) запускает Long Poll и SQL worker вместе. Демо в консоли остаётся доступным через `run_bot.cmd`. Нужны Python 3.12+, интернет и настройки `.env`: `VK_TOKEN`, `VK_GROUP_ID`, `ADMIN_IDS`. Модель, Docker, отдельный gateway и INTERNAL_API_KEY для этого режима не нужны. SQLite автоматически создаёт локальную `gim.db`. В сообщениях сообщества напишите `/start`; команды сотрудника: `/admin`, `/top`, `/candidate ID`, `/export`, `/stats`. Для доступа к отправке уведомлений сотрудник сначала открывает сообщения сообщества и пишет боту.

На этом компьютере VK-настройки уже внесены в исключённый `.env`; токен в документации не публикуется. Read-only проверка 2026-10-21 подтвердила сообщество, Long Poll API 5.199 и message_new. Прохождение реального опроса и получение Excel проверяются отдельно. На другом ПК заполните собственный `.env` по `.env.example`. `DATABASE_URL` по умолчанию использует SQLite, для серверной нагрузки нужен PostgreSQL.

python -m venv .venv

Демо использует настоящую FSM и SQLite, создаёт только локальный `demo.db`; для проверки вводите вымышленные данные. Продолжение после перезапуска работает. `/delete` → `УДАЛИТЬ` удаляет заявку. SQLite предназначена для локальной проверки; рабочая установка использует PostgreSQL.

## Подготовка сообщества ВК

Создайте сообщество для тестирования от имени владельца проекта, включите сообщения сообщества, создайте токен сообщества с разрешениями сообщений и документов. В настройках Bots Long Poll включите приём новых входящих сообщений (`message_new`). Запишите числовой ID сообщества и VK ID сотрудников. Интерфейс настроек ВК может меняться; проверить права реального токена необходимо перед запуском.

Скопируйте `.env.example` в `.env`, заполните `VK_TOKEN`, `VK_GROUP_ID`, `ADMIN_IDS` (числа через запятую). `POSTGRES_PASSWORD` нужен только для Docker/PostgreSQL, `INTERNAL_API_KEY` — только для необязательного отдельного gateway. Для пароля БД и внутреннего ключа используйте длинные случайные hex-строки; не публикуйте `.env` и не показывайте полный `docker compose config` с заполненными секретами. `DATABASE_URL` внутри Compose собирается из пароля автоматически.

Музей должен согласовать точный текст `CONSENT_TEXT`, условия передачи содержательных ответов провайдеру и срок хранения до приглашения реальных кандидатов. Техническая ссылка на существующую политику не означает юридической проверки согласия.

## Запуск на сервере

Нужны Docker Engine и Compose v2. Команды выполняются из корня репозитория:

```bash
docker compose config --quiet
docker compose up --build -d --scale worker=2
docker compose ps
docker compose logs --tail=100 bot worker
```

Один контейнер `bot` получает Long Poll. `worker` масштабируется процессами; каждый по умолчанию выполняет до 5 задач. Необязательный `llm-gateway` доступен через Compose profile llm; по умолчанию при отключённой модели не запускается. Числа конфигурируются, гарантий пропускной способности внешних API они не дают. Порты PostgreSQL и необязательного gateway на хост не публикуются. Все контейнеры приложения непривилегированные, с файловой системой только для чтения; данные в named volume PostgreSQL.

В текущей среде Docker отсутствует: сборка образа и реальный запуск Compose ещё не подтверждены. Есть синтетические тесты, но это не нагрузочная сертификация выбранного сервера или VK.

## Очередь и отказоустойчивость

Redis и ARQ удалены из кода, зависимостей, Compose и локальной venv. Работает SQL-очередь background_jobs, без отдельного брокера.

## Языковая модель

Для текущего запуска оставьте `LLM_API_KEY` и `LLM_MODEL` пустыми. Внешние LLM-запросы не выполняются. Модельный клиент сохранён для следующего этапа; его включение требует отдельной настройки и проверки качества.

Если ключ/модель не настроены, gateway недоступен, превышен таймаут или ответ нарушает схему/цитаты, основной опрос и библиотечные уточнения работают. Заявка сохраняется **без аналитики**: балл отсутствует, ноль не подставляется. Позже не запускается бесконечная платная переоценка. Все задания хранятся в SQL. Worker подбирает их раз в секунду, атомарно назначает одному процессу и восстанавливает аренду после аварии. Не более трёх попыток, timeout задачи 120 с, аренда 10 минут; финальные ошибки — в background_jobs и логах. Уведомления и отправка сообщений используют устойчивые ключи идемпотентности. Анализ имеет lease 10 минут для восстановления после аварии worker.

Чувствительные поля исключаются из модельного payload, контакты внутри свободного текста маскируются. Это не абсолютная гарантия анонимности произвольного текста: содержание опыта само по себе может позволять идентификацию. Внешний кэш отключён; ответы и токены не логируются.

Ответы кандидату отправляются через SQL outbox: ошибка доставки не удерживает общий Long Poll `ts`. До пяти попыток с паузами; устаревший недоставленный вопрос заменяется актуальным. После доставки/окончательного отказа текст и прямой VK ID из outbox очищаются. При удалении заявки сохраняются только технические хэши обработанных событий, чтобы replay не восстановил ответы; новое событие согласия может начать новую анкету. Синхронную команду просмотра сотрудник при недоставке повторяет самостоятельно; сохранённый запрос Excel восстанавливается фоновой сверкой.

## Команды

Кандидат: `Старт`, `/start`, `/status`, `/delete` с подтверждением. Сотрудник в личном сообщении сообществу: `/admin`, `/top 10`, `/candidate 1`, `/export`, `/stats`. ID сотрудника должен присутствовать в `ADMIN_IDS`; общий чат не принимается как административный интерфейс.

После завершения куратор получает `+1 заполненная заявка`. Excel приходит документом, содержит исходные и уточняющие ответы, балл, рубрику, причины с цитатами, направление, резюме, вопросы для интервью и отдельную сводку. Строки кандидата записываются как текст, формулы из них не исполняются.

## Резервирование и восстановление

Пример для Bash на сервере; хранить дамп в закрытом каталоге, ограничить срок и доступ по правилам музея:

```bash
docker compose exec -T postgres pg_dump -U gim -d gim -Fc > gim-backup.dump
```

Проверку восстановления проводить в отдельной тестовой БД, а не поверх работающего музея. Для нового пустого экземпляра с базой `gim`:

```bash
docker compose exec -T postgres pg_restore -U gim -d gim --no-owner < gim-backup.dump
```

Запускайте бота после восстановления. Очередь заново сверяется с PostgreSQL. Удаление кандидатом не уничтожает уже скачанные сотрудником Excel и предыдущие резервные копии: жизненный цикл этих копий определяет музей. При обновлении схемы требуется отдельная миграция; `create_all` создаёт только первую схему и не заменяет миграции.

## Проверка качества

`python -m gim_bot.evaluate --csv '/path/2024.csv' --csv '/path/2025.csv' --output results/evaluation.json` читает локальные файлы и сохраняет только агрегаты. По умолчанию выполняет инвентаризацию и majority-baseline на фиксированном holdout; платные вызовы разрешаются только флагом `--llm` при заполненных ключе и модели. Признаки берутся из allowlist, последующие результаты участия и экспертный балл не отправляются модели. Персональные исходники не копировать в репозиторий.

До живого запуска остаются: VK smoke, выбранная модель и цена, сравнение с экспертами (H003), реальные 5–7 минут (H001), нагрузка PostgreSQL/VK и тест backup/restore на сервере. Отсутствующие проверки не считаются пройденными.

## Текущий тестовый процесс

Бот запущен на этом ПК фоном, без Redis и модели. Проверьте /start в сообщениях сообщества, /admin и /export для сотрудника. Управляемый фоновый процесс останавливается через stop_vk.cmd; повторный ручной запуск — run_vk.cmd. Одновременно допускается один локальный poller (повторный запуск покажет сообщение «уже запущен»). Логи — gim_bot/runtime/ в родительском проекте, runtime/ в самом checkout; секреты и runtime исключены из Git. Пройти полный опрос и получить Excel пока должен тестирующий пользователь.
