## 1. Найди доступ и подготовь секреты локально

Проверь доступные Supabase-коннекторы и уже настроенные секреты именно этого проекта. Проверяй наличие конфигурации без печати значений. Не перебирай посторонние личные файлы. Publishable/anon/Storage API key не является паролем PostgreSQL.

Если есть операторское SQL-подключение, используй его только для настройки/миграций. Для них нужен session pooler5432 или direct connection, не transaction pooler. Фактические endpoint, username и режим SSL проверь в Connect, не считай документацию гарантией текущих настроек.

Создай три отдельных runtime LOGIN, каждый наследует ровно одну роль: gim_bot, gim_worker, gim_staff. Используй `database/scripts/provision_runtime.py` и локальный закрытый файл `database/private/runtime-credentials.json`; пароли генерируй программно криптографическим генератором, не в тексте ответа. Если LOGIN уже существует, сначала выясни его назначение и возможность повторного использования; скрипт намеренно не перезаписывает чужие роли. Не сбрасывай существующие пароли автоматически, не выдавай SUPERUSER/BYPASSRLS/ADMIN OPTION.

Операторский DSN/пароль не включай в runtime `.env`, контейнеры, образ, отчёты и Git. Сервисные DSN запиши только локально в `gim_shared/.env`: DATABASE_BOT_URL, DATABASE_WORKER_URL, DATABASE_STAFF_URL. Используй URL-encoding паролей или штатный conninfo builder. Для Supabase runtime проверь transaction pooler6543, SSL и правильное имя LOGIN с project ref. Отключение prepared statements уже реализовано. Разные пользовательские роли сначала проверь реальными соединениями.

Если доступен только MCP с SQL, используй его допустимые возможности настройки, но не выдавай вымышленный operator DSN за рабочий. Без возможности получить/создать пригодные runtime подключения настройку нельзя объявлять завершённой; не проси присылать пароль в чат, предложи локальное секретное хранилище/файл.
