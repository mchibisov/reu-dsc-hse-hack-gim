# Промпт разработчику: MVP VK-бота ГИМ

Ты разрабатываешь рабочую первую версию VK-бота предварительного отбора волонтёров Государственного исторического музея. Источник требований — `docs/specs/S002-gim-vk-bot.md`; при расхождении с иллюстрациями и старыми заметками следуй последним согласованным решениям этой спецификации. Перед кодом прочитай правила проекта, составь связанный SDD-план, затем реализуй и проверь его. Пользователь уже поручил начинать MVP.

Срок — 12 часов, ориентир бюджета около 2000 рублей; 90 одновременно проходящих опрос кандидатов. Все взаимодействия — личные сообщения сообщества ВК. Сообщество и токены предстоит подготовить; не выдумывай наличие доступов или состоявшееся развёртывание.

**Актуальный этап:** пользователь отложил Mistral. Запускай без внешней LLM: библиотечные уточнения, сохранение ответов, Excel, сводка и уведомления. Балл оставляй null; не создавай модельное резюме и рекомендации. Описанная ниже аналитика — следующий этап, её наличие не является условием текущего запуска.

Кандидат даёт согласие и отвечает на исходные вопросы музея. Сохрани все смысловые поля и каждый ответ, условно спрашивай неприменимые сведения об образовании. Опрос целиком с уточнениями должен занимать 5–7 минут; фактическое время проверяй на людях. После основной анкеты используй библиотеку музейных уточнений и LLM-персонализацию по конкретному прошлому опыту, hard/soft skills и интересующему направлению. Не повторяй известное, не устраивай ситуационные задания. Поясни реальные задачи направления и уточни альтернативы при интересе только к фондам. Пять направлений: мероприятия, квесты и мастер-классы, фонды, инклюзия, медиа. Кандидату отправляй только подтверждение получения анкеты.

Куратору по закрытым командам `/top`, `/candidate ID`, `/export`, `/stats` доступны отсортированные анкеты, оценка 0–3, резюме, рекомендуемое направление, причины с дословными цитатами, вопросы для интервью и сводка. При завершении заявки отправляй уведомление. Ручных правок балла/направления/заметок, сайта, PDF и загрузки резюме нет. Не посещай страницу ВК кандидата. Решение о приёме остаётся человеку.

LLM разбирает свободный текст, оценивает соответствие пяти заранее заданным группам критериев музея, готовит резюме и вопросы. Критерии не придумывает; уровни и цитаты проверяются приложением, итоговый балл вычисляется детерминированно. Версионируй рубрику. Неизвестные признаки не объявляй отрицательными фактами. Исторические часы, удержание, принятие и явка не входят в признаки новой заявки. Не выдавай предварительную численную рубрику и самоотчёты о навыках за проверенную точность или доказанную компетентность.

Если модель недоступна, проведи опрос с библиотечными уточнениями и сохрани заявку со статусом «без аналитики», без балла и выдуманного резюме. Подтверждай отправку только после записи в БД.

Архитектура: Python async, bot-процесс Long Poll, внутренний LLM gateway с JSON Schema и таймаутами, фоновые ARQ workers, Redis, PostgreSQL, Docker Compose. Несколько workers обслуживают конкурирующие задачи; один потребитель Long Poll. FSM/валидация/сохранение — обычный код, не LLM. Секреты из env; ACL по ID сотрудников; удаление заявки по подтверждению; без PII в логах, модельном payload и Git. Excel защищён от формул пользователя. Нужны идемпотентность, восстановление состояния, ограниченные повторы, сверка потерянных фоновых задач и backup/restore.

Пиши тесты до реализации. Проверь согласие, полный диалог, персонализацию, границы оценки, неизвестные критерии, вымышленные цитаты, чужие команды, дубли событий, перезапуск, сбой LLM, экспорт и конкурентные заявки. Для каждой проверки сохраняй отдельный отчёт и обезличенные доказательства в `results/`, заранее фиксируй гипотезы в журнале. Сравнивай с экспертными баллами на отложенных данных без утечки; точность не объявляй без фактического измерения. Перед передачей проведи независимое ревью и сообщи, что проверено локально, а что требует реального VK, модели и сервера.
