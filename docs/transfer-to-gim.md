# Передача проекта Государственному историческому музею

Рабочий вариант — VK Callback на Vercel + PostgreSQL в Supabase + Polza. Для сервера музея готов Docker/Long Poll. Код, публичный банк вопросов, миграции и инструкции находятся в `main`; заполненные анкеты и секреты в репозиторий не входят.

## Что передаётся

| Составляющая | Где находится |
|---|---|
| Код, Dockerfile, Compose, миграции и тесты | Репозиторий GitHub |
| Анкета и пять направлений без персональных данных | `config/museum-bank.json` |
| Формула оценки | `config/ranking-50-35-15.json` |
| Инструкции кандидата и сотрудника | `docs/user-guide.md`, `docs/admin-guide.md` |
| Быстрый локальный запуск | `docs/docker-quickstart.md` |
| Облачное развёртывание | `docs/deployment-guide.md` |
| Метрики, безопасность и приёмка | `docs/evaluation-report.md`, `docs/security-review.md`, `output/` |
| Аватарка и иллюстрации | `assets/branding/` |

## 1. Доступ сотрудника музея

Действующий администратор проверяет числовой VK ID сотрудника ГИМ и отправляет `/staff add VK_ID admin`. Сотрудник разрешает сообщения сообщества, открывает `/admin`, `/top`, карточку и `/export`. После подтверждения доступа удаляются лишние роли команды командой `/staff remove VK_ID` — последний администратор защищён от удаления.

Это передаёт работу с заявками, но не владение GitHub, сообществом и облачными аккаунтами.

## 2. Владение инфраструктурой и секреты

Ответственный ГИМ получает права на сообщество VK, репозиторий/организацию GitHub и проекты Vercel/Supabase. Если перенос между аккаунтами провайдера недоступен, создаётся новый проект под учётной записью музея по инструкции развёртывания.

Передаются через согласованный защищённый канал или менеджер секретов:

- токен сообщества VK;
- три ограниченных runtime-подключения PostgreSQL;
- ключ Polza;
- Callback secret, confirmation и dispatch key;
- код Excel, если он используется;
- операторское подключение БД — отдельно, только ответственному оператору.

Секреты не вставляются в презентацию, Git, публичный README или переписку с кандидатами. После передачи ключи ротируются согласованно: сначала новые значения в среде/хранилище, затем проверка, затем отзыв старых. Для worker dispatch должны совпасть значение в Vercel и Supabase Vault.

## 3. Резервная копия и перенос данных

До переключения сохраняются полная резервная копия БД, миграционная история, активный набор, незавершённые анкеты и очередь. Для Docker также сохраняются конфигурационный volume с runtime-паролями и volume Excel. Для облака XLSX находятся в приватной таблице `gim.file_contents` и входят в копию БД. Восстановление предварительно проверяется в отдельной БД.

Нельзя объединять старую альтернативную схему и схему `gim` простой заменой DATABASE_URL. Не запускать quickstart поверх рабочей Supabase: он предназначен для новой локальной БД и отклоняет чужую установку. На существующей рабочей БД используются только проверенные добавочные миграции с контролем checksum. Автоматически пересчитывать старые оценки не требуется.

## 4. Контролируемое переключение

1. Собрать и проверить новую версию, пока старая продолжает обслуживать VK.
2. Подготовить переменные, роли и миграции; проверить доступность БД и защищённость HTTP-маршрутов.
3. Убедиться в наличии резервной копии и прежнего рабочего образа/deployment для отката.
4. Переключить один транспорт: Callback или Long Poll. Два потребителя для одного сообщества одновременно не запускать.
5. Пройти приёмочный сценарий ниже. При ошибке вернуть прежний образ и транспорт, сохранив очередь и ответы.

Для нового Docker-сервера — одна команда из `docker-quickstart.md`; для подготовленной внешней Supabase — `compose.yaml`. Для Vercel — `deployment-guide.md`; Functions должны находиться рядом с БД (для текущего проекта fra1).

## 5. Приёмка музеем

- Новый кандидат: согласие → 18 вопросов → проверка ожиданий → персональные уточнения → подтверждение подачи.
- Сотрудник: «+1 анкета» → AI-сводка → карточка с проверяемыми цитатами → рейтинг → XLSX с пятью листами.
- Ручное изменение оценки сохраняет AI-оригинал; тестовый сброс архивирует только собственную попытку.
- Обычный кандидат не открывает чужие карточки и экспорт. Отозванный сотрудник теряет доступ.
- Временная ошибка LLM не теряет анкету и не создаёт оценку 0.
- После перезапуска прохождение продолжается; повтор события не создаёт повторный ответ.

## 6. Регламент эксплуатации

Назначаются ответственные за очередь/ошибки, баланс Polza, квоты хостинга, резервные копии и обращения по данным. Ежедневно проверяется `/jobs`, периодически — восстановление копии. Условия бесплатных тарифов и пригодность для постоянной работы музея подтверждаются владельцем аккаунтов; бесплатность не является гарантией безлимитной эксплуатации.

До начала реального набора музей утверждает текст согласия, порядок хранения и удаления данных, использование внешней модели и рубрику. Формула 50/35/15 задана командой; новая независимая точность не подтверждена. Окончательное решение о приёме всегда принимает сотрудник. Код не подменяет эти организационные решения.
