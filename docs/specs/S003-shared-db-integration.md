# S003: интеграция существующего VK-бота и общей БД

- Основание: пользователь поручил отправить код в репозиторий, прочитать существующего бота и использовать загруженную БД.
- База: origin/max/database-mvp 6220cc3, включает Vova ff0b44b. Новый checkout gim_shared, ветка codex/shared-db-integration; действующий gim_bot не переключается до проверки новой среды.
- Границы: использовать private gim schema и Repository/Storage контракт database/, не создавать public legacy-таблицы. Четыре применённые миграции не редактировать. Redis/ARQ удалить из нового runtime, модель отключена. Без сайта/PDF/загрузки резюме и ручной правки балла в текущем VK UI.
- R301: основной опрос из question_templates с сохранением точных dialog_questions/answers, повтор VK-event идемпотентен и не отвечает на следующий вопрос; данные и consent сохраняются по API Repository.
- R302: максимум 3 библиотечных уточнения по прошлому опыту, затем submit; нет выдуманной оценки, summary и LLM-запросов.
- R303: SQL outbox с claim, lease_token, heartbeat/возврат после аварии, конечные попытки; единственный исполнитель, без Redis. Дополнительные runtime-поля/таблица checkpoint только новой миграцией.
- R304: закрытые /admin /top /stats /application (/candidate alias) /export; staff API проверяет настоящий VK ID и группу. Не предоставлять /score, PDF и файлы кандидата через новый UI.
- R305: существующий контракт export_bundle/request_export/FileRepository; XLSX хранится приватно локально по умолчанию (ключ Storage отсутствует), явно не выдавать его за загрузку в Supabase Storage; VK отправка с устойчивым random_id.
- R306: существующий Long Poll VK-клиент, SQL checkpoint и аренда gateway, несколько worker; Windows launcher, .env aliases. Не применять старые migrations/*.sql к новому Supabase.
- R307: новая роль БД и миграции проверяются на отдельной PostgreSQL; все результаты/ограничения сохраняются. Нет доступа к облачной БД до предоставления сервисных DSN; API keys не заменяют пароль БД.
- R308: коммит и push своей ветки после тестов и проверки секретов. Сейчас GitHub API push=false, обычный git push --dry-run даёт 403 для mirovif; владелец должен выдать права или сменить локальную авторизацию. Никаких обходов или force-push.

## Важные ограничения исходного контракта

Private DB требует consent и возраст 18+ для submit; это условие существующей схемы и должно быть отражено в ошибке пользователю, не выдаётся за новый LLM-критерий. Банк/рубрика/recruitment должны быть заранее загружены оператором; приложение их не придумывает и не активирует автоматически. Неизвестно, есть ли сейчас активный набор в облаке.
